값 타입과 참조 타입

값을 제자리에 두는 타입과 힙에 두는 타입, 둘을 잇는 boxing을 익힌다

학습 목표

이 모듈을 학습하면 다음을 할 수 있다.

  1. 값 타입과 참조 타입의 저장 위치를 그림으로 비교할 수 있다.
  2. FloatOrInt 공용체에 3.14를 쓰고 int32로 읽을 때의 값을 구할 수 있다.
  3. newobj와 boxing이 JVM 방식과 다른 점을 대가와 함께 설명할 수 있다.

값 타입과 참조 타입의 저장 위치논문 6, 7절

Point 하나를 만들면 그 값은 어디에 놓일까? 공통 언어 기반(Common Language Infrastructure, CLI)의 값 타입(Value Type)은 C의 struct나 Pascal의 record처럼 이름 붙은 필드의 묶음이며, 변수가 있는 그 자리에 할당한다. 참조 타입(Reference Type)의 객체는 늘 가비지 컬렉션(Garbage Collection, GC)이 관리하는 힙(Heap)에 할당한다.

그림은 값 타입 지역 변수 p와 참조 타입 지역 변수 f의 저장 위치를 나타낸 것이다(값 3, 5는 예시).

표는 두 타입의 차이를 나타낸 것이다. (논문 6, 7절)
기준값 타입참조 타입
놓이는 곳변수 자리(제자리)늘 GC 힙
대입하면필드 값 전체를 복사주소만 복사(같은 객체 공유)
요약

값 타입은 필드를 변수 자리에 바로 담고, 참조 타입은 객체를 GC 힙에 두고 변수에는 주소만 담는다.

구조체, 열거형, initobj논문 6.1, 6.3, 6.4절

구조체(Struct) Point는 int 필드 x, y를 담는다. CLI는 필드를 어떤 순서로든 저장할 수 있다.

.class value Point {
  .field public int x
  .field public int y
}

initobj T는 스택의 주소가 가리키는 값 타입의 모든 필드를 0이나 null로 채운다. 타입 하나에 매이지 않는 polytypic 명령어의 예이다.

.locals (valuetype Point p)
ldloca p        // 스택: [&p]
initobj Point   // 스택: [ ], p = (0, 0)

열거형(Enum)은 이름과 정수 값을 타입 안전하게 묶는다. 내부 저장 타입과 비트 집합 여부도 정할 수 있다.

.class enum Shape {
  .field public static valuetype Shape RECTANGLE = int32(0)
  .field public static valuetype Shape CIRCLE = int32(1)
}
요약

구조체와 열거형은 값 타입으로 선언하고, initobj는 주소가 가리키는 값 타입을 한 번에 0으로 채운다.

공용체: 같은 4바이트를 겹쳐 쓴다논문 6.2절

공용체(Union, 필드가 같은 메모리를 겹쳐 쓰는 타입)는 필드 배치를 직접 정하는 explicit로 만든다. 아래 FloatOrInt의 두 필드는 모두 바이트 위치 0([0])에서 시작한다.

.class value explicit FloatOrInt {
  .field [0] public float32 f
  .field [0] public int32 n
}

그림은 FloatOrInt의 4바이트(높은 자리부터, 메모리 안 순서는 기계마다 다름)와 3.14의 IEEE-754 비트를 나타낸 것이다. 1078523331은 계산 값이다.

요약

FloatOrInt의 f와 n은 같은 4바이트를 쓰므로, f에 3.14를 쓰면 n으로는 그 비트 패턴인 1078523331이 읽힌다.

핵심 질문
  • stfld와 ldfld는 스택에서 무엇을 꺼내는가?
  • 왜 n은 3이 아닌가?
  • 이런 코드는 안전한가?
더 알아보기

이 기법은 타입 안전하지 않다. 판별자 없는 공용체의 이런 사용은 검증기(Verifier)가 허용하지 않으므로, 신뢰하지 않는 코드에서는 쓸 수 없다(7단원).

탐구 자료float으로 쓰고 int로 읽기논문 6.4절

지역 변수는 .locals (valuetype FloatOrInt fi, int32 n)이다. 평가 스택(Evaluation Stack) 상태를 함께 보며 버튼을 눌러 한 줄씩 따라가시오.

CIL (논문 코드) // fi.f = 3.14 ldloca fi ldc.r4 3.14 stfld float32 FloatOrInt::f // n = fi.n ldloca fi ldfld int32 FloatOrInt::n
설명과 스택

앞 절반은 f에 3.14를 쓰는 부분이다.

fi의 주소를 올린다. 스택 [&fi]

float32 상수 3.14를 올린다. 스택 [&fi, 3.14]

둘을 꺼내 바이트 0~3에 3.14를 쓴다. 스택 [ ]

뒤 절반은 같은 자리를 n으로 읽는 부분이다.

다시 fi의 주소를 올린다. 스택 [&fi]

&fi를 꺼내 바이트 0~3을 int32로 읽는다. 스택 [1078523331]

n은 3.14의 비트를 그대로 정수로 읽은 값이다. n에 넣으려면 stloc n이 더 필요하다.

요약

stfld로 f에 쓴 3.14를 ldfld로 n에서 읽으면 같은 비트가 정수 1078523331로 읽히며, 이 코드는 검증할 수 없다.

JVM에서 값 타입 흉내 내기논문 6.4절

논문은 값 타입이 enum, 레코드, 공용체가 있는 Pascal이나 C 같은 언어를 컴파일하는 데 꼭 필요하다고 주장한다. 당시 자바 가상 머신(Java Virtual Machine, JVM)에는 값 타입이 없었다.

표는 C·Pascal의 기능을 두 플랫폼에서 표현하는 방법을 나타낸 것이다. (논문 6.4절)
기능CLI당시 JVM
열거형.class enum 값 타입클래스로 흉내(비효율)
구조체·레코드.class value 값 타입클래스로 흉내(힙 객체)
공용체.class value explicit클래스 계층으로 흉내
float을 쓰고 int로 읽기가능(검증할 수 없음)불가능

핵심 비교 CLI는 값 타입으로 바이트 배치까지 그대로 옮기고, JVM은 클래스로 흉내 내므로 비효율적이고 겹쳐 쓰기는 아예 표현하지 못한다.

요약

JVM은 값 타입을 클래스로 흉내 내야 해 비효율적이고, 공용체의 겹쳐 쓰기는 표현할 수 없다.

참조 타입: Foo와 Bar논문 7절

참조 타입에는 클래스(Class), 인터페이스(Interface), 배열, 대리자(Delegate, 메서드를 가리키는 타입 안전 객체)가 있고, 논문은 클래스만 다룬다. Bar는 Foo를 상속하며 두 클래스는 같은 네 메서드를 정의한다.

.class public Foo {
  .method public virtual void f() {...}
  .method public instance void g() {...}
  .method public static void h() {...}
  .method public specialname void .ctor() {...}
}
.class public Bar extends Foo {
  .method public virtual void f() {...}
  .method public instance void g() {...}
  .method public static void h() {...}
  .method public specialname void .ctor() {...}
}
표는 Foo의 메서드 종류를 나타낸 것이다. 호출 명령어와의 관계는 6단원에서 다룬다. (논문 7, 8절)
종류예호출할 구현을 정하는 기준비슷한 언어
가상 메서드(Virtual Method)f실행 때 객체의 실제 타입Eiffel, Java
인스턴스 메서드(Instance Method)g선언된 타입(this는 받음)C++
정적 메서드(Static Method)h클래스 이름(this 없음)Eiffel, Java
생성자(Constructor).ctornewobj가 부름모든 클래스
요약

CLI 클래스는 가상, 인스턴스, 정적 메서드를 모두 가질 수 있고, 생성자는 늘 specialname을 붙인 .ctor이다.

탐구 자료newobj와 JVM의 객체 생성논문 7.1절

newobj c는 생성자 c의 클래스 인스턴스를 할당하고 필드를 초기화한 뒤, 새 인스턴스와 인수로 생성자를 부른다. 아래 b의 정적 타입은 Foo, 실제 객체는 Bar이다.

.locals (class Foo f, class Foo b)
newobj void Foo::.ctor(); stloc f
newobj void Bar::.ctor(); stloc b

그림은 각 명령어 뒤의 스택을 나타낸 것이다(점선 칸은 초기화 전 객체, JVM의 저장은 예시).

JVM은 늘 new c; dup; invokespecial c.<init>()V 순서를 써야 한다. 그래서 검증기는 복잡한 데이터 흐름 분석(Dataflow Analysis)으로 초기화 전 사용과 두 번 초기화를 막아야 한다. 논문은 할당과 초기화를 한 명령어로 묶어 이 복잡함을 처음부터 피하는 편이 단순하다고 주장한다.

요약

newobj는 할당과 초기화를 한 명령어로 끝내 미초기화 객체가 스택에 드러나지 않게 한다.

boxing과 unboxing논문 9절

Point를 컬렉션에 넣으려면 값 타입을 참조 타입 자리에 써야 한다. Scheme 같은 동적 언어와 Haskell, SML 같은 다형 함수형 언어도 다형 함수가 모든 인수를 같은 모양으로 받기를 기대하므로 같은 문제를 겪는다.

boxing(값을 객체로 감싸기)은 택배 상자에 물건을 넣듯 값을 힙의 상자 객체에 복사한다. unboxing(객체에서 값을 꺼내기)은 반대 방향이다.

그림은 Point 값을 boxing하고 다시 unboxing하는 과정을 나타낸 것이다(값 3, 5는 예시).

대가로 box 한 번마다 힙 할당 한 번과 필드 복사가 일어난다. 논문은 값을 넘길 때마다 클래스 인스턴스를 직접 만드는 방식은 부담이 너무 크므로 런타임이 boxing을 기본으로 지원해야 한다고 주장한다. 당시 JVM은 boxing을 지원하지 않았다.

요약

box는 값을 힙의 상자 객체로 복사해 object로 쓰게 하고, unbox는 되돌리며, 그 대가로 할당과 복사가 든다.

핵심 정리
  1. 값 타입은 제자리에, 참조 타입은 늘 GC 힙에 할당한다.
  2. explicit 배치의 공용체는 같은 바이트를 겹쳐 쓰며, 이를 이용한 기법은 검증할 수 없다.
  3. newobj는 할당과 초기화를 한 명령어로 묶는다.
  4. boxing은 값을 힙으로 복사하므로 할당 비용이 든다.
  5. 공용체 문제는 같은 비트를 어떤 타입으로 읽는지부터 확인하라.
