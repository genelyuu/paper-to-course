스레드는 활성 레코드의 연결 리스트논문 2절

공통 언어 기반(Common Language Infrastructure, CLI)은 여러 스레드(Thread)를 동시에 관리하며, 이 스레드가 꼭 운영체제의 스레드일 필요는 없다. 논문은 스레드를 활성 레코드(Activation Record, 스택 프레임)가 한 방향으로 이어진 연결 리스트로 본다. 메서드를 부르는 명령어가 새 레코드를 만들어 현재 레코드에 잇고, 호출이 끝나면 그 레코드를 없앤다.

그림은 Main이 F를, F가 G를 부른 순간의 스레드를 나타낸 것이다. 화살표는 호출한 쪽으로 되돌아가는 연결이다.

보통은 한 스레드의 활성 레코드를 런타임 스택에 잡지만, CLI는 레코드 관리를 추상화해 두었으므로 반드시 그럴 필요는 없다. 그래서 논문은 혼동을 피하려고 “스택”이라는 말을 평가 스택에만 쓴다. 이 강의도 같은 약속을 따른다.

요약

CLI의 스레드는 활성 레코드의 연결 리스트이고, 레코드는 호출로 생겨 반환, tail call, 예외로 사라진다.

활성 레코드 안의 여덟 칸논문 2절

논문은 활성 레코드가 여덟 가지 요소로 이루어진다고 설명한다. 실행 위치를 가리키는 명령어 포인터(Instruction Pointer, IP), 계산 중간값을 쌓는 평가 스택(Evaluation Stack), 메서드가 쓰는 지역 변수(Local Variable)와 호출자가 넘긴 인수(Argument)가 그 예이다. 그림에서 강조한 두 배열이 JVM과 구조가 가장 다르다.

그림은 논문 2절이 든 활성 레코드의 구성 요소 여덟 가지를 나타낸 것이다. 칸의 배치는 메모리 순서가 아니다.

요약

활성 레코드는 IP, 평가 스택, 지역 변수 배열, 인수 배열, methodInfo, 지역 메모리 풀, 반환 상태, 보안 기술자로 이루어진다.

탐구 자료구성 요소가 하는 일논문 2절

표는 활성 레코드의 구성 요소마다 하는 일과 JVM과의 차이를 나타낸 것이다.
구성 요소하는 일JVM과 비교
① 명령어 포인터(IP)현재 메서드에서 다음에 실행할 명령어를 가리킨다같은 역할
② 평가 스택계산의 중간값을 쌓는다JVM은 operand stack이라 부른다
③ 지역 변수 배열어떤 타입이든 담지만, 한 변수는 한 타입으로만 쓴다JVM은 한 칸에 정수를 넣었다가 실수를 넣을 수 있다
④ 인수 배열호출자가 넘긴 인수를 담는다JVM은 인수와 지역 변수가 한 배열이다
⑤ methodInfo 핸들시그니처, 지역 변수의 타입, 예외 처리기 정보를 가리킨다논문은 비교하지 않는다
⑥ 지역 메모리 풀메서드 안에서 객체를 동적으로 할당한다(localloc, 6단원)논문은 비교하지 않는다
⑦ 반환 상태 핸들반환할 때 호출자의 상태를 되살린다컴파일러 용어로 동적 링크
⑧ 보안 기술자assert, permit-only, deny 같은 보안 재정의를 기록한다managed code는 직접 읽을 수 없다

핵심 비교 CLI는 인수와 지역 변수를 나누고 각 칸의 타입을 고정한다. 그래서 검증기는 칸마다 한 타입만 따지면 된다(해석, 7단원).

요약

CLI의 활성 레코드는 인수와 지역 변수를 따로 두고 칸마다 타입을 고정한다는 점에서 JVM과 다르다.

저장 위치의 크기: 4바이트 칸 대 다형적 칸논문 2절

논문에 따르면 JVM은 지역 변수, 스택 칸, 인수를 모두 4바이트 칸에 둔다. 그래서 8바이트인 long과 double은 칸 두 개를 차지한다(JVM 명세의 배경 지식). CLI의 저장 위치는 담는 값에 따라 4바이트에서 사용자 정의 값 타입(Value Type)의 수백 바이트까지 크기가 다르지만, 프레임이 살아 있는 동안 타입은 고정된다.

그림은 지역 변수 int a, long b, double c를 두 기계가 담는 방식을 나타낸 예시이다.

핵심 비교 JVM에서는 b를 1, 2번 칸에 걸쳐 두므로 c는 3번이 되지만, CLI에서는 b가 1번, c가 2번 지역 변수이다. 크기가 큰 값 타입도 위치 하나에 그대로 담는다.

요약

JVM은 모든 저장 위치가 4바이트라 long과 double이 두 칸을 쓰고, CLI는 크기가 다른 위치 하나에 타입을 고정해 담는다.

어셈블리: CLI의 소프트웨어 부품논문 3절

어셈블리(Assembly)는 공통 중간 언어(Common Intermediate Language, CIL) 코드와 메타데이터(Metadata)를 담은 모듈(Module, 어셈블리를 이루는 파일)의 묶음이다. 컨테이너 화물에 목록표가 붙듯, 어셈블리에는 자신을 설명하는 매니페스트(Manifest)가 붙는다.

매니페스트에는 버전, 구성 파일, 밖으로 내보내는 타입이 적히고, 선택적으로 디지털 서명(Digital Signature)과 공개 키(Public Key)도 들어간다.

그림은 논문 3절이 설명한 어셈블리의 구성과, 어셈블리 단위로 이루어지는 네 가지 일을 나타낸 것이다.

요약

어셈블리는 CIL 코드와 메타데이터를 담은 모듈의 묶음에 매니페스트를 붙인 것으로, 보안과 버전 등이 이 단위로 처리된다.

보충 설명

응용 프로그램 도메인(Application Domain)은 한 프로세스 안에서 프로그램을 격리하는 단위로, 논문은 이를 “프로세스”라고도 부른다.

탐구 자료ILASM으로 쓴 매니페스트 읽기논문 3절

논문은 ILASM(CIL 어셈블러 문법)으로 쓴 매니페스트를 예로 든다. 다음 줄 버튼을 누르며 한 줄씩 읽어 보자.

ILASM .assembly HelloWorld {} .assembly extern mscorlib { .publickeytoken = (B7 7A 5C 56 19 34 E0 89) .ver 1:0:2411:0 }
설명

이 어셈블리 자신의 이름을 HelloWorld로 선언한다. 중괄호 안은 비어 있다.

extern은 이 어셈블리가 참조하는 다른 어셈블리를 뜻한다. 여기서는 기본 라이브러리인 mscorlib 어셈블리이다.

참조할 어셈블리를 공개 키에서 얻은 8바이트 토큰으로 특정한다(해석). 이름이 같아도 만든 쪽이 다르면 구별된다.

참조할 버전을 주.부.빌드.수정 번호의 네 수로 적는다(해석).

외부 어셈블리 선언을 닫는다.

자기 이름은 .assembly로, 참조하는 어셈블리는 .assembly extern으로 적는다. 참조 쪽에 공개 키 토큰과 버전을 함께 적으므로, 런타임은 이름만이 아니라 누가 만든 몇 번째 버전인지로 어셈블리를 찾는다.

요약

ILASM 매니페스트는 .assembly로 자기 이름을, .assembly extern으로 참조 대상을 공개 키 토큰과 버전으로 적는다.

어셈블리와 JAR 파일논문 3절

논문은 어셈블리를 JVM의 JAR(Java Archive) 파일과 대략 비교할 수 있다고 말한다. 표는 논문이 든 어셈블리의 특징을 JAR 파일과 나란히 놓은 것이다.

표는 어셈블리와 JAR 파일을 다섯 가지 기준으로 비교한 것이다. JAR 열은 강의가 덧붙인 배경 설명이다.
기준어셈블리(논문 3절)JAR 파일(배경)
묶는 것CIL 코드와 메타데이터를 담은 모듈클래스 파일과 자원
자기 설명매니페스트(버전, 구성 파일, 내보내는 타입, 서명)압축 파일 안의 매니페스트 파일
단위로 하는 일보안, 버전, 타입 해석, 응용 프로그램 도메인주로 배포와 클래스 경로
최상위 메서드·필드클래스 밖에 둘 수 있다모든 메서드와 필드가 클래스 안에 있다
메타데이터 확장custom attribute로 사용자가 늘린다2001년 당시 Java에는 없었다

어셈블리 안에는 클래스, 인터페이스, 배열, delegate 같은 참조 타입과 구조체, 열거형 같은 값 타입, 중첩 타입을 정의한다. 논문은 메타데이터를 custom attribute(사용자 정의 특성)로 사용자가 확장할 수 있다는 점을 CLI만의 특징으로 든다. 이는 2001년 기준의 주장이며, 이후 Java도 비슷한 annotation을 들였다.

요약

어셈블리는 JAR 파일과 비슷한 배포 단위이지만, 최상위 메서드와 필드를 허용하고 custom attribute로 메타데이터를 확장한다.

핵심 정리

  3. JVM의 칸은 4바이트, CLI의 위치는 크기가 다르고 타입이 고정된다.
  4. 칸 수 문항은 long과 double이 JVM에서 두 칸임을 먼저 센다.
