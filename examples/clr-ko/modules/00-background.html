이 논문을 쓴 이유와 새로운 점논문 1절

자바 가상 머신(Java Virtual Machine, JVM)은 여러 언어 구현자가 실행 환경으로 택했지만, 저자들은 JVM이 다중 언어 플랫폼으로는 본질적으로 최적이 아니라고 주장한다. 이 논문은 처음부터 다중 언어용으로 설계한 공통 언어 기반(Common Language Infrastructure, CLI)를 JVM과 비교한다. 논문은 명세인 CLI와 Microsoft의 구현인 공통 언어 런타임(Common Language Runtime, CLR)을 섞어 쓰며, CLI용 코드는 공통 중간 언어(Common Intermediate Language, CIL)이다.

이 논문의 새로운 점
  1. 처음부터 다중 언어 설계: 개발 초기부터 언어 구현자와 협력했고, tail call(꼬리 호출) 명령어는 그 의견으로 추가했다(1절).
  2. JVM에 없는 기본 연산: 참조 전달용 포인터, 값 타입과 공용체, 오버플로 감지 산술, tail call을 명령어 수준에서 제공한다(4~10절).
  3. 검증과 비검증의 공존: 검증 가능한 부분집합으로 안전을 보장하고, 필요하면 포인터도 허용한다(11절).
요약

저자들은 JVM이 여러 언어를 올리기에 최적이 아니라고 보고, 처음부터 다중 언어용으로 설계한 CLI를 소개한다.

컴파일러, 인터프리터, 가상 머신

컴파일러(Compiler)는 원천 코드를 실행 전에 네이티브 코드(Native Code, 특정 CPU의 기계어)로 한꺼번에 번역한다. 인터프리터(Interpreter)는 번역해 두지 않고 명령을 하나씩 읽으며 바로 실행한다. 기계어는 CPU마다 달라서, 컴파일한 프로그램은 다른 CPU에서 돌지 않는다.

가상 머신(Virtual Machine, VM)은 소프트웨어로 만든 가상의 기계이고, 그 기계의 명령어로 쓴 코드가 중간 언어(Intermediate Language)이다. JVM의 바이트코드(Bytecode)와 CLI의 CIL이 그 예이다. 컴파일러는 중간 언어까지만 번역하고, 기계어로 바꾸는 마지막 단계는 실행하는 기계의 VM이 맡는다.

그림은 같은 원천 코드를 실행하는 세 가지 방식을 나타낸 것이다. CLI는 셋째 줄의 방식이다.

요약

가상 머신 방식은 컴파일러가 CPU와 무관한 중간 언어를 만들고, 실행하는 기계의 VM이 마지막 번역을 맡는다.

번역기 수 세기: n×m 대 n+m

그림은 논문 1절의 이식성 주장을 언어 3개, 플랫폼 3개의 예시로 센 것이다.

$$T_{\mathit{direct}} = n \times m$$

직접 번역하면 언어 하나와 플랫폼 하나의 짝마다 번역기를 따로 만든다. 왼쪽 그림처럼 행이 $n$개, 열이 $m$개인 표의 모든 칸이 번역기이다.

$$T_{\mathit{IL}} = n + m$$

중간 언어를 두면 언어마다 “원천 코드 → 중간 언어” 앞단 하나, 플랫폼마다 “중간 언어 → 기계어” 뒷단 하나만 있으면 된다. 곱이 덧셈으로 바뀐다.

$$n = m = 3:\quad 3 \times 3 = 9, \qquad 3 + 3 = 6$$

그림의 예시 값을 넣으면 9개와 6개이다. 3개 차이는 작아 보이지만, 단서 칸의 표처럼 $n$과 $m$이 커지면 차이가 빠르게 벌어진다.

$$n \times m - (n + m) = (n-1)(m-1) - 1$$

아낀 번역기 수는 $(n-1)(m-1)-1$개이다. $n=m=10$이면 80개를 아낀다. 새 언어 하나를 더할 때도 직접 번역은 번역기 $m$개, 중간 언어는 앞단 1개만 새로 만들면 된다.

요약

중간 언어를 두면 언어 n개와 플랫폼 m개를 잇는 번역기가 n×m개에서 n+m개로 준다.

스택 머신(Stack Machine)은 계산의 중간값을 평가 스택(Evaluation Stack)에 쌓는다. 명령어는 스택 맨 위의 값을 꺼내 계산하고 결과를 다시 맨 위에 올린다. 그림의 접시 더미처럼 넣고 빼는 곳은 맨 위 한 곳뿐이다.

JIT 컴파일: 실행 직전에 기계어로

JIT(Just-In-Time) 컴파일러(실행 직전에 기계어로 번역)는 메서드가 처음 불릴 때 그 메서드의 CIL을 기계어로 번역해 두고, 다음 호출부터는 번역한 기계어를 바로 실행한다. 인터프리터는 같은 명령을 실행할 때마다 다시 읽고 해석한다. 그림은 같은 메서드를 세 번 부를 때 두 방식이 쓰는 시간을 나타낸 것이다.

표는 인터프리터와 JIT를 네 가지 기준으로 비교한 것이다.
기준인터프리터JIT
첫 실행까지바로 시작한다번역 시간만큼 늦다
같은 코드 반복매번 다시 해석한다번역한 기계어를 다시 쓴다
기계에 맞춘 최적화어렵다실행할 CPU를 보고 번역한다(논문의 효율 이유)
대가반복 실행이 느리다번역 시간과 기계어를 둘 메모리가 든다

핵심 비교 인터프리터는 시작이 빠르고, JIT는 반복이 빠르다. 4단원에서 보듯 CIL 명령어는 타입을 적지 않는 경우가 많아 JIT가 할 일이 그만큼 늘어난다.

타입 안전성, GC, managed code

타입 안전성(Type Safety)은 값을 선언한 타입대로만 쓰게 보장하는 성질이다. 정수를 주소처럼 쓰거나 객체에 없는 필드를 읽는 일을 막으므로, 엉뚱한 메모리를 건드리는 오류가 생기지 않는다.

실행 중에 만든 객체는 힙(Heap)에 놓인다. GC는 어떤 변수에서도 닿지 않는 객체를 찾아 자동으로 회수하고, 빈틈을 줄이려고 살아 있는 객체를 옮기기도 한다. 그래서 GC 힙 안의 주소는 고정되어 있지 않다(4단원 포인터의 전제).

managed code(CLR이 관리하는 코드)는 GC, 타입 검사, 보안을 CLR이 맡아 관리하는 코드이다. C의 포인터 연산처럼 CLR이 관리하지 않는 코드는 unmanaged code라 부른다. CLI는 두 코드가 함께 동작하도록 설계했다.

요약

타입 안전성은 값을 타입대로만 쓰게 하고, GC는 닿지 않는 객체를 회수하며 객체를 옮길 수 있고, managed code는 이 관리를 CLR에 맡긴 코드이다.
