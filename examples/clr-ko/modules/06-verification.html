검증

검증기가 CIL에서 무엇을 확인하고 무엇을 거부하는지, 그리고 논문의 결론을 어떻게 읽을지 살핀다

학습 목표

이 모듈을 학습하면 다음을 할 수 있다.

  1. 검증이 보장하는 것과 런타임 검사로 넘기는 것을 구분할 수 있다.
  2. 합류 지점에서 평가 스택의 높이와 타입을 판정할 수 있다.
  3. 논문의 결론을 실험 없는 주장으로 비판적으로 읽을 수 있다.

검증은 언제, 누구를 믿지 않고 하는가논문 11절

검증(Verification)은 공통 중간 언어(Common Intermediate Language, CIL) 코드가 메모리 안전성을 해치지 않는지 실행 전에 분석하는 일이다. 논문에 따르면 검증은 배포나 로드 때 하며 만든 사람을 신뢰하지 않는다. JVM처럼 분석은 보수적이지만 특정 종류의 런타임 오류가 없다는 강한 보장을 준다.

논문은 검증의 보장이 엄격한 정적 타입 언어의 보장과 비슷하다고 쓴다.

  • 객체 참조(Object Reference)를 담는 위치는 선언한 타입의 계약을 만족하는 객체만 가리킨다.
  • 필드(Field) 선택은 알려진 타입에 실제로 있는 필드만 접근한다.
요약

검증기는 배포나 로드 때 생산자를 믿지 않고 CIL을 분석해, 참조와 필드 접근이 타입에 맞는지 보장한다.

핵심 질문
  • 검증기가 미리 증명하지 못하는 것은 무엇인가?
  • 그런 경우 검증기는 무엇을 확인하는가?

정적 보장과 런타임 검사논문 11절

배열 인덱스가 늘 배열 크기 안에 있음을 미리 증명하기는 거의 불가능하다. 그래서 검증기는 이런 접근이 범위 검사(Bounds Check)로 보호되는지를 확인한다. 축소 형변환(Narrowing Cast, 상위 타입을 하위 타입으로 바꾸기)이 성공해야만 가능한 필드·메서드 접근도 같은 원리를 따른다.

확인할 것언제 확인하나방법
참조가 선언 타입에 맞는가검증 때(정적)타입 흐름 분석
필드가 그 타입에 있는가검증 때(정적)메타데이터와 대조
배열 인덱스가 범위 안인가실행 때범위 검사가 있는지 검증기가 확인
축소 형변환이 맞는가실행 때형변환 검사 뒤에만 접근 허용
 표는 검증기가 정적으로 보장하는 것과 런타임 검사에 맡기는 것을 나타낸 것이다. (논문 11절)
요약

정적으로 증명할 수 없는 배열 인덱스와 축소 형변환은 런타임 검사로 보호되는지를 검증기가 확인한다.

핵심 질문
  • 두 경로가 만나는 곳에서 스택은 어떤 조건을 지켜야 하는가?
  • 서로 다른 객체 타입이 만나면 정적 타입은 무엇이 되는가?

탐구 자료합류 지점의 평가 스택논문 11절

if/else처럼 제어 흐름(Control Flow)이 갈라졌다가 만나는 곳을 합류 지점(Merge Point)이라 한다. 여기서 모든 경로의 평가 스택은 높이가 같고 타입이 호환되어야 한다. 객체 참조는 들어오는 타입들의 최소 공통 조상(Least Common Ancestor)이 정적 타입이 된다. 아래 예에서 Bar와 Baz는 모두 Foo를 상속한다(Baz는 예시). 탭을 눌러 비교하시오.

높이가 1로 같고 두 타입이 모두 객체 참조이다. 정적 타입은 최소 공통 조상인 Foo가 되므로, 합류 뒤에는 Foo의 필드와 메서드만 쓸 수 있다.

한 경로만 값을 하나 더 올렸다. 합류 뒤 명령어가 스택에서 몇 개를 꺼낼지 정할 수 없으므로 검증기는 이 코드를 거부한다.

높이는 같지만 정수와 객체 참조는 공통 조상이 없어 호환되지 않는다. 정수를 참조로 쓰는 길이 열리므로 검증기는 거부한다.

요약

합류 지점에서는 스택 높이가 같고 타입이 호환되어야 하며, Bar와 Baz가 만나면 정적 타입은 최소 공통 조상 Foo가 된다.

핵심 질문
  • 어떤 명령어와 사용법이 검증을 통과하지 못하는가?
  • 공용체는 왜 일부만 검증할 수 있는가?

검증할 수 없는 코드논문 11절, 각주 3

CLI는 타입 안전한 기능과 타입 안전하지 않은 기능을 모두 제공한다. 검증 가능한 CIL을 만들려면 컴파일러가 다음을 피해야 한다. 이것이 4~5단원에서 본 unmanaged pointer, 주소 산술, 공용체의 대가이다.

피해야 할 것왜 검증할 수 없나
block copy 명령어본질적으로 검증할 수 없는 명령어임
add를 주소 산술에 쓰기덧셈 자체는 괜찮지만 결과 주소가 어디를 가리킬지 모름
타입 안전하지 않은 대입선언 타입의 계약을 깨는 값이 들어감
판별자 없는 공용체(Union)의 일부 사용참조와 다른 타입이 겹치면 정수로 가짜 참조를 만들 수 있음
 표는 검증 가능한 코드를 만들 때 피해야 할 것을 나타낸 것이다. (논문 11절)
요약

block copy, 주소 산술, 타입 안전하지 않은 대입, 참조를 겹치는 공용체는 검증을 통과하지 못한다.

핵심 질문

  • reference surrogate의 대가는 무엇인가?

값을 참조로 대신하기: reference surrogate논문 11절

논문은 정적으로 타입 안전한 언어라면 늘 검증 가능한 CIL로 컴파일할 수 있다고 본다. 다만 데이터 타입을 옮길 때 궁리가 필요하다. 예는 크기가 정적으로 정해진 값 배열이다(Pascal의 ARRAY [0..3] OF INTEGER 같은 것, 예시).

값 객체를 참조 타입으로 나타내는 이 관용구를 논문은 reference surrogate(값을 대신하는 참조 객체)라 부르고, 자세한 대응은 [10]에 미룬다. 대가로 힙 할당이 생기고, 대입할 때 값처럼 복사되도록 컴파일러가 따로 맞춰야 한다고 해석할 수 있다.

요약

검증기가 주소 산술을 막으므로, 값 배열은 같은 크기의 참조 배열(reference surrogate)로 바꿔 CLI 내장 배열을 쓴다.

핵심 질문

  • 검증된 환경에서도 남는 CLR의 기능은 무엇인가?

peverify와 첫 시도 부트스트랩논문 11절

오프라인 검증기 peverify는 CIL을 만드는 코드에서 흔히 생기는 오류 대부분을 찾아 진단한다. 논문은 Project 7 컴파일러 중 하나인 Gardens Point Component Pascal이, peverify가 CIL을 검증 가능하다고 확인하자 첫 시도에 자기 자신을 부트스트랩(Bootstrap, 컴파일러가 자기 자신을 컴파일)했다고 소개한다.

논문이 강조하는 점은 CLR 혁신의 대부분이 검증된 환경에서도 유지된다는 것이다. 값 클래스(5단원), managed pointer로 넘기는 참조 매개변수(4단원 Swap), 참조를 다른 타입과 겹치지 않는 공용체가 그 예이다.

요약

peverify는 CIL 생성기의 오류를 잡아 주며, 값 클래스·참조 매개변수·타입 안전한 공용체는 검증된 환경에서도 쓸 수 있다.

핵심 질문

결론과 읽을 때의 주의논문 12절

저자들은 앞 절들의 논증으로 CLI가 다중 언어 플랫폼으로서 이미 JVM보다 엄밀히 더 강력하다고 주장한다. 그리고 지금 JVM을 대상으로 하는 사람까지 포함한 언어 구현자들에게 CLI를 대상으로 삼아 의견을 달라고 요청한다.

살필 점내용읽는 법
근거의 종류명령어와 설계의 비교 설명. 실험이나 수치 비교가 없음“더 강력하다”는 저자의 주장으로 읽는다
저자의 이해관계Microsoft 소속과 CLR 컴파일러 저자(Gough는 [10]의 저자)이해관계가 있는 비교임을 감안한다
시점2001년, JVM 명세 2판 기준이후 바뀐 점은 8단원에서 확인한다
저자가 인정한 한계명령형·정적 타입 OO 언어 지원은 좋고, 비표준 패러다임 지원은 개선 중([16])“완벽한 다중 언어 플랫폼”은 아니라는 단서
 표는 12절 결론을 읽을 때 살필 점을 정리한 것이다. (논문 1, 12절과 해석)

핵심 비교 논문이 보인 것은 “CLI에는 이런 명령어가 있고 JVM에는 없다”는 설계 비교이며, 그 차이가 실제 언어 구현에서 얼마나 이득인지는 측정하지 않았다.

그래도 tail call, 값 타입, 참조 매개변수처럼 논문이 짚은 차이는 구체적인 명령어로 확인할 수 있다. 이 점에서 논문은 다중 언어 실행 환경이 갖출 기본 연산의 목록을 제시한 문서로 해석할 수 있다.

요약

“JVM보다 엄밀히 더 강력하다”는 결론은 실험 없는 설계 비교에 기댄 저자의 주장이며, 이해관계와 2001년 시점을 감안해 읽는다.

핵심 정리
  1. 검증은 배포나 로드 때 생산자를 믿지 않고 하며, 증명할 수 없는 것은 런타임 검사로 보호되는지 확인한다.
  2. 합류 지점에서는 스택 높이가 같고 타입이 호환되어야 하며, 객체 참조는 최소 공통 조상이 정적 타입이 된다.
  3. 주소 산술 같은 기능은 검증할 수 없으므로 reference surrogate 같은 대응이 필요하다.

합류 문항은 경로마다 스택을 아래부터 적어 높이와 타입을 맞춰 보라.
