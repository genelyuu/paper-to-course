메서드 호출과 특수 명령어

호출 명령어가 실행할 메서드를 고르는 방식과 tail call, 함수 포인터 같은 특수 기능을 살핀다

학습 목표

이 모듈을 학습하면 다음을 할 수 있다.

  1. call, call instance, callvirt가 실행할 메서드를 고르는 시점을 비교할 수 있다.
  2. tail call이 스택 프레임을 다루는 방식과 그 한계를 설명할 수 있다.
  3. ldftn, calli, jmp, localloc, ldtoken이 어떤 언어 기능을 돕는지 설명할 수 있다.

같은 변수, 두 가지 타입논문 7, 8절

5단원의 Foo와 Bar를 다시 쓴다. Foo에는 가상 메서드(Virtual Method) f, 인스턴스 메서드(Instance Method) g, 정적 메서드(Static Method) h가 있고, Bar는 Foo를 상속해 셋을 모두 다시 정의한다.

지역 변수 bar를 class Foo로 선언하고 Bar 객체를 담으면, 이 변수에는 타입이 두 개 생긴다. 선언이 정한 정적 타입(Static Type, 선언된 타입)은 Foo이고, 실제 객체가 정한 동적 타입(Dynamic Type, 실제 객체의 타입)은 Bar이다.

호출 명령어는 이 두 타입 중 무엇을 보고 메서드를 고르는지가 다르다. 정적 타입으로 고르면 early binding(컴파일 때 호출 대상 결정), 동적 타입으로 고르면 late binding(실행 때 호출 대상 결정)이다.

요약

변수 bar의 정적 타입은 Foo, 동적 타입은 Bar이며, 호출 명령어는 둘 중 하나를 보고 메서드를 고른다.

핵심 질문
  • 같은 bar에 명령어만 바꾸면 무엇이 실행되는가?
  • callvirt가 늘 late binding인가?

탐구 자료명령어를 바꾸면 실행되는 메서드논문 8절

세 호출 모두 먼저 ldloc bar로 Bar 객체를 평가 스택에 올리고, 이 값이 호출된 메서드의 this가 된다. 탭을 눌러 명령어를 바꾸고 실행되는 메서드를 비교하시오.

early binding. 정적 타입 Foo만 보고 Foo::f()를 부른다. bar가 Bar 객체여도 Bar::f()는 실행되지 않는다(JVM의 invokespecial과 비슷).

late binding. 명령어에는 Foo::f()라고 적혀 있지만 this의 동적 타입이 Bar이므로 Bar::f()가 실행된다.

g는 가상 메서드가 아닌 인스턴스 메서드이다. 논문에 따르면 인스턴스 메서드에 callvirt를 써도 early binding이므로 Foo::g()가 실행된다.

정적 메서드는 this가 없으므로 ldloc bar가 필요 없다. 명령어에 적힌 Foo::h()가 그대로 실행된다(JVM의 invokestatic에 해당).

요약

같은 Bar 객체라도 call instance는 Foo::f(), callvirt는 Bar::f()를 실행하며, 인스턴스 메서드에는 callvirt도 early binding이다.

JVM 호출 명령어와의 대응논문 8절

당시 자바 가상 머신(Java Virtual Machine, JVM)은 호출 대상의 종류마다 명령어를 따로 두었다. 공통 언어 기반(Common Language Infrastructure, CLI)은 직접 호출을 call과 callvirt 두 개로 묶고, 함수 포인터 호출 calli를 따로 둔다.

핵심 비교 JVM은 클래스 메서드와 인터페이스 메서드의 가상 호출을 두 명령어로 나누지만, CLI는 callvirt 하나로 처리한다.

논문은 JVM이 두 명령어로 나눈 탓에 “컴파일러 작성자가 다시 한번 고생한다”고 쓴다. 대가도 있다. 명령어 이름만으로는 가상 호출인지 알 수 없으므로, 대상 메서드가 가상인지 인스턴스인지를 메타데이터에서 확인하는 일은 JIT(Just-In-Time) 컴파일러의 몫이 된다고 해석할 수 있다.

요약

JVM의 invokevirtual과 invokeinterface는 CLI에서 callvirt 하나가 되고, 메서드 종류를 가리는 일은 JIT로 넘어간다.

탐구 자료tail call과 스택 프레임논문 8.1절

Haskell, Scheme, Mercury처럼 재귀가 유일한 반복 수단인 언어에서는 함수의 마지막 동작이 다시 호출인 tail call(꼬리 호출, 함수의 마지막 동작인 호출)이 반복문 역할을 한다. tail. 접두사는 JIT에게 호출 전에 호출한 쪽의 활성 레코드(Activation Record, 스택 프레임)를 버리라고 지시한다.

.method public static void Bottom() {
  .maxstack 8
  tail. call void Bottom(); ret
}

논문에 따르면 이 메서드는 스택 오버플로(Stack Overflow) 예외 없이 영원히 돈다. 탭을 눌러 프레임 수를 비교하시오.

요약

tail.이 있으면 JIT가 호출한 쪽 프레임을 버려 프레임 수가 늘지 않고, JVM은 trampoline으로 같은 효과를 흉내 낸다.

핵심 질문
  • tail call이 프레임을 버리지 못하는 경우는 언제인가?
  • trampoline은 무엇을 대가로 치르는가?

tail call의 한계와 JVM의 우회논문 1, 8.1절

논문은 tail. 명령어를 언어 연구자들의 의견을 받아 직접 넣었다고 밝힌다. 그러나 신뢰하지 않는 코드가 신뢰하는 코드를 부를 때는 보안 때문에 호출한 쪽 프레임을 완전히 버릴 수 없다.

논문은 JVM에서는 trampoline 같은 편법으로 “JVM이 프레임을 버리도록 억지로” 만들어야 한다고 쓴다(참고문헌 [5, 27, 15, 18]).

요약

tail.은 보안 경계에서 프레임을 다 버리지 못하고, JVM의 trampoline은 호출마다 반환과 재호출을 치른다.

함수 포인터: ldftn, calli, jmp논문 10절

CLI에는 단일 구현 상속과 여러 인터페이스 구현을 위한 가상 dispatch(호출할 메서드 고르기)가 들어 있다. 그 밖의 방식을 쓰는 언어는 디스패치 테이블(Dispatch Table)을 직접 만든다. ldftn은 함수 포인터(Function Pointer)를 평가 스택에 올리고, calli는 스택 맨 위의 함수 포인터를 호출한다.

jmp는 메서드 참조를 받아 그 메서드의 진입점으로 제어를 옮긴다. 다중 상속(Multiple Inheritance)에서는 부모마다 객체 안의 위치가 달라 this를 옮겨야 하는데, 논문은 이 일을 하는 trampoline stub을 jmp로 만든다고 쓴다. 대가로 calli는 대상이 실행 중에 정해지므로 호출 시그니처를 명령어에 따로 적어야 한다(해석).

요약

ldftn과 calli로 언어마다 다른 디스패치 테이블을 만들고, jmp로 다중 상속의 this 조정 stub을 만든다.

localloc과 ldtoken논문 10절

conformant array(크기를 호출 때 정하는 배열 매개변수)를 값으로 넘기는 언어는 호출 때 배열 복사본을 둘 공간이 필요하다. localloc은 현재 활성 레코드를 늘려 그 공간을 만들며, C의 alloca와 의미가 같다.

ldtoken은 명령어 인수에 적힌 타입 참조의 런타임 타입 핸들을 스택에 올린다. 인스턴스 없이 타입 정보가 필요할 때 쓰는 reflection(실행 중에 타입 정보를 조회·사용)의 기본 부품이다.

기준CLI ldtoken TJVM Class.forName("T")
타입을 가리키는 것명령어 인수의 타입 참조(메타데이터)문자열 이름
이름을 묶는 시점실행 전 메타데이터에 고정실행 시점
 표는 타입 정보를 얻는 두 방식을 비교한 것이다. (논문 10절과 해석)
요약

localloc은 힙 대신 활성 레코드를 늘려 복사본을 두고, ldtoken은 타입을 이름 문자열이 아니라 메타데이터 참조로 가리킨다.

핵심 정리
  1. call instance는 정적 타입, callvirt는 this의 동적 타입으로 가상 메서드를 고른다. 인스턴스 메서드에는 callvirt도 early binding이다.
  2. tail.은 호출한 쪽 프레임을 버리지만 보안 경계에서는 완전히 버리지 못한다.
  3. ldftn·calli·jmp·localloc·ldtoken은 다른 방법으로 합성하기 어려운 언어 기능을 돕는다.
