CLI의 타입과 포인터, 명령어가 값을 옮기고 계산하는 방식을 익힌다

학습 목표

이 모듈을 학습하면 다음을 할 수 있다.

  1. CLI 포인터 세 종류의 차이를 GC와 관련지어 설명할 수 있다.

기본 타입논문 4절

타입 생성자와 자연 크기 타입논문 4절

기본 타입은 타입 생성자(Type Constructor, 타입을 조합해 새 타입을 만드는 규칙)로 묶어 더 큰 타입이 된다.

표는 CLI의 타입 생성자를 나타낸 것이다. 이 단원은 색칠한 포인터를 다룬다. (논문 4절)

자연 크기 타입(Natural-Size Type)은 크기 결정을 미루는 장치이다. JIT(Just-In-Time) 컴파일러(실행 직전에 기계어로 번역)가 공통 중간 언어(Common Intermediate Language, CIL) 코드를 번역할 때 프로세서를 보고 크기를 정한다.

그림은 같은 CIL이 프로세서마다 다른 크기로 정해지는 과정을 나타낸 것이다(칸 하나가 1바이트). object, &, *도 같은 방식으로 정해진다.

요약

타입 생성자는 기본 타입을 묶어 새 타입을 만들고, 자연 크기 타입은 크기 결정을 JIT 시점까지 미룬다.

포인터 세 종류: object, &, *논문 4절

왜 CLI는 포인터를 세 종류로 나눌까? object는 GC가 관리하는 객체 참조(Object Reference)이다. managed pointer(관리 포인터, T&)는 객체 내부도 가리키며, GC가 힙의 경계를 알기 때문에 힙 밖을 가리켜도 안전하다.

unmanaged pointer(비관리 포인터, T*)는 다른 런타임의 전통적인 주소로, 네이티브 코드(Native Code, 특정 CPU의 기계어)와 함께 일하는 데 꼭 필요하다. 다만 GC가 객체를 옮기고 압축하므로 GC 힙 안은 가리킬 수 없다.

그림은 세 포인터가 가리키는 곳을 나타낸 것이다(이름과 값 7은 예시). GC가 객체를 옮기면 o와 r(교과 색, 객체 내부)이 함께 고쳐지고, p는 GC 힙 밖의 버퍼만 가리킨다.

요약

object는 객체 전체를, managed pointer는 객체 내부와 힙 밖을, unmanaged pointer는 GC 힙 밖의 주소만 가리킨다.

탐구 자료세 포인터와 JVM의 참조 타입논문 4절

표는 같은 기준으로 CLI의 세 포인터와 JVM의 참조 타입을 비교한 것이다. JVM은 모든 포인터를 참조 타입 하나로 묶는다.

표는 포인터 종류별 성질을 비교한 것이다. (논문 4절, 7단원 검증 내용 포함)

요약

다형 명령어와 load/store 계열논문 5, 5.1절

CLI 명령어는 약 220개이다. JVM은 명령어 이름에 인수 타입을 박아 넣지만, CLI는 다형 명령어(피연산자 타입에 따라 동작이 정해지는 명령어)를 쓰고 보통 결과 타입만 적는다.

그 덕분에 컴파일러는 CIL을 만들기 쉽다. 대가로 JIT가 할 일이 늘어난다. JIT가 평가 스택(Evaluation Stack)의 타입을 추적해 어떤 덧셈인지 정해야 하기 때문이다.

JVM은 반대로 해석은 쉽지만 컴파일러마다 부담이 된다.

값을 평가 스택에 올리는 명령어를 load(스택에 올리기), 꺼내 저장하는 명령어를 store(스택에서 꺼내 저장)라 한다.

표는 load/store 계열을 대상별로 나타낸 것이다. n은 번호, t는 타입의 짧은 이름이다. (논문 5.1절)

요약

CLI는 다형 명령어로 컴파일러의 일을 덜고 JIT의 일을 늘리며, load/store 명령어가 값과 주소를 평가 스택으로 옮긴다.

보충 설명

메서드 머리는 .method static void Swap(int32& xa, int32& ya)이고, 지시어 .maxstack 2, .locals (int32 z)가 이어진다. C#으로 쓰면 Swap(ref x, ref y)(예시)이다.

탐구 자료의사코드 단계별 풀이: Swap논문 5.1절

Swap은 두 변수의 값을 맞바꾼다. 참조 전달(Pass by Reference)로 받은 주소를 역참조(Dereference)해 읽고 쓴다. x=3, y=5(예시 값)라 하고 버튼을 눌러 한 줄씩 보시오. 주석은 실행 뒤의 스택(왼쪽이 바닥)이다.

CIL (논문 코드) ldarg xa // [&x] ldind.i4 // [3] stloc z // [ ] z=3 ldarg xa // [&x] ldarg ya // [&x, &y] ldind.i4 // [&x, 5] stind.i4 // [ ] x=5 ldarg ya // [&y] ldloc z // [&y, 3] stind.i4 // [ ] y=3 ret // return
설명

인수 xa에 든 주소 &x를 올린다.

&x를 꺼내 역참조하고 x의 값 3을 올린다.

3을 꺼내 지역 변수 z에 둔다.

값을 쓸 곳인 &x를 다시 올린다.

&y를 올린다. 높이가 2가 된다.

&y를 꺼내 역참조하고 5를 올린다.

5와 &x를 꺼내 x에 5를 쓴다.

값을 쓸 곳인 &y를 올린다.

z에 둔 옛 x 값 3을 올린다.

3과 &y를 꺼내 y에 3을 쓴다.

빈 스택으로 호출한 쪽에 돌아간다.

요약

Swap은 주소를 역참조해 x를 z에 맡기고, y를 x에, z를 y에 써서 두 값을 바꾼다.

탐구 자료Swap의 스택 상태와 JVM의 우회책논문 5.1절

그림은 x=3, y=5(예시 값)일 때 각 명령어 뒤의 평가 스택(아래가 바닥)과 변수 값을 나타낸 것이다. &x, &y는 int32& 타입, 숫자는 int32 타입이며 교과 색 칸은 주소로 읽어 온 값이다.

호출하는 쪽은 지역 변수의 주소를 ldloca로 넘긴다. 당시 JVM은 지역 변수의 주소를 얻을 수 없어 원소 하나짜리 배열이나 box 클래스로 흉내 내야 했다(Gough [12]).

.locals (int32 x, int32 y)
// initialize x and y
ldloca x
ldloca y
call void Swap(int32&, int32&)
// JVM 우회책 (Java 예시)
int[] xa = { x }, ya = { y };
swap(xa, ya);
x = xa[0]; y = ya[0];
// swap 안: int z = xa[0];
//   xa[0] = ya[0]; ya[0] = z;
요약

CLI는 지역 변수 주소를 넘겨 스택 두 칸으로 Swap을 끝내고, 당시 JVM은 배열을 새로 만들어 값을 넣고 다시 꺼내야 했다.

산술 오버플로와 분기논문 5.2, 5.3절

add는 스택 맨 위 두 값을 꺼내 더한다. 정수 오버플로(Overflow)는 .ovf(부호 있음)나 .ovf.un(부호 없음)을 붙여야 감지한다. 부동소수점 오버플로는 +∞나 −∞가 된다.

당시 JVM은 정수 오버플로를 알리지 않았다. 그래서 감지가 필요한 Ada95나 SML은 연산마다 검사 코드를 넣어야 해 시간 손해가 클 수 있다고 논문은 지적한다.

표는 2147483647 + 1을 명령어별로 계산한 결과이다(계산 값). 마지막 줄은 float32 최댓값 약 3.4 × 1038을 두 번 더한 예이다.
명령어값의 해석결과
add부호 있는 int32, 검사 없음−2147483648 (비트 0x80000000, 조용히 넘어감)
add.ovf부호 있는 int32범위를 넘으므로 오버플로 예외
add.ovf.un부호 없는 32비트2147483648은 범위 안이므로 예외 없음
add (float32)float32 최댓값 + 최댓값(예외 없음)+∞

분기(Branch) 명령어로는 br, beq, bge 등이 있다. CLI에는 JVM의 서브루틴(Subroutine) 점프 jsr가 없고, JVM처럼 분기 거리를 64K로 제한하지도 않는다. 논문은 이 제한이 사람에게는 작은 문제지만 JVM 바이트코드(Bytecode)를 만드는 컴파일러에는 실제 문제라고 지적한다.

요약

CLI는 오버플로 감지를 명령어 접미사로 고르게 하고, 분기 거리에 64K 제한을 두지 않는다.

핵심 정리
  1. 자연 크기 타입은 크기를 JIT 시점에 정한다.
  2. &는 객체 내부와 힙 밖을 가리키고 GC가 고쳐 주며, *는 힙 밖만 가리킨다.
  3. 다형 명령어는 컴파일러의 일을 덜고 JIT의 일을 늘린다.
  4. ldloca와 ldind, stind로 참조 전달을 직접 구현한다.
  5. 스택 문제는 명령어마다 꺼내는 개수와 올리는 개수를 세어 풀어라.
