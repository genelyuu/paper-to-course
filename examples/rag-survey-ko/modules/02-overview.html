RAG 개요

RAG의 전체 구조와 세 가지 발전 단계, 다른 최적화 방법과의 차이를 살핀다

학습 목표

이 모듈을 학습하면 다음을 할 수 있다.

  1. RAG 구조도의 오프라인·온라인 흐름과 단계별 입력·출력을 설명할 수 있다.
  2. 세 가지 RAG 발전 단계의 차이를 같은 단계 축에서 비교할 수 있다.
  3. RAG, 모델을 추가 학습하는 방법, 프롬프트를 다듬는 방법의 쓰임을 구별할 수 있다.

RAG의 전체 구조논문 2절

RAG 시스템은 문서를 미리 준비하는 오프라인 단계와 질문을 받아 답하는 온라인 단계로 나뉜다. 오프라인에서는 문서를 청크(Chunk)로 자르고 임베딩해 벡터 데이터베이스(Vector Database)에 넣으며, 이 준비 과정을 indexing(색인 구축)이라 한다.

온라인에서는 retriever(검색기)가 청크를 찾고, generator(생성기)인 LLM이 답을 만든다. 그림은 이 흐름과 상자별 값(예시)을 나타낸 것이다. 교과 색 칸은 질문과 청크를 하나로 묶는 증강 단계이다.

출처: 논문 그림 2, LangChain RAG 튜토리얼(Load-Split-Store, Retrieve-Generate)(https://docs.langchain.com/oss/python/langchain/rag)을 참고해 다시 그림.

요약

RAG는 문서를 청크로 잘라 벡터 데이터베이스에 넣어 두고, 질문이 오면 가까운 청크를 찾아 프롬프트에 붙여 LLM이 답하게 한다.

핵심 질문
  • 질문 하나는 단계마다 무엇으로 바뀌는가?
  • indexing은 질문 전에 하는가, 후에 하는가?

Naive RAG의 세 단계: 질문 하나 따라가기논문 2.1절

가장 단순한 형태인 Naive RAG는 앞의 구조도를 한 번씩 거친다. 스페이스바로 한 줄씩 넘기시오.

알고리즘 INPUT: D, q, k chunks = SPLIT(CLEAN(D)) index = STORE(EMBED(chunks)) v = EMBED(q) top = TOPK(index, v, k) prompt = CONCAT(q, top) OUTPUT: LLM(prompt)
설명

D는 사내 규정 120건, q는 “신입 사원의 연차는 며칠인가?”, k는 3이다(예시).

[indexing] 512토큰씩 자르면 청크 1,840개이다. c17은 “제12조 ① 입사 1년 미만은 매월 1일…”이다.

청크 1,840개를 768차원 벡터로 바꿔 벡터 데이터베이스에 저장한다.

[검색] indexing 때와 같은 임베딩 모델로 q를 768차원 벡터 v로 바꾼다.

v와 코사인 유사도가 큰 순서로 c17(0.89), c18(0.84), c52(0.41)을 고른다.

[생성] q와 청크 3개를 한 프롬프트로 묶는다(약 620토큰).

LLM이 “1년 미만은 매월 1일, 이상은 연 15일(제12조)”이라고 답한다.

요약

Naive RAG는 문서를 청크로 잘라 저장하고, 질문과 가까운 청크 k개를 찾아 프롬프트에 넣어 답을 만든다.

핵심 질문
  • Naive RAG는 어느 단계에서 실패하는가?
  • 검색이 정확해도 답이 나빠질 수 있는가?

탐구 자료Naive RAG의 한계논문 2.1절

그림은 논문이 꼽은 Naive RAG의 한계를 단계별로 나타낸 것이다. 검색 단계에서는 precision(정밀도)과 recall(재현율)이 낮아 무관한 청크가 섞이고 필요한 청크를 놓친다(두 지표의 계산은 2단원 ‘지표 읽는 법’에서 다루었다). 생성 단계에서는 검색 내용과 맞지 않거나 검색 내용을 되풀이하기만 하는 답이 나온다.

세 문제는 단계마다 따로 생기지만 서로 이어진다. 검색이 무관한 청크를 가져오면 생성 단계가 그 청크를 근거로 환각을 만들 수 있으므로, 뒤의 두 패러다임은 주로 검색 품질부터 고친다고 해석할 수 있다.

요약

Naive RAG는 검색의 precision·recall, 생성의 faithfulness(답이 문맥에 충실한 정도), 여러 청크를 잇는 증강에서 모두 한계를 보인다.

핵심 질문
  • Advanced RAG는 Naive RAG에 무엇을 더했는가?
  • Modular RAG는 무엇을 바꿀 수 있게 하는가?

Naive, Advanced, Modular RAG 비교논문 2절

Advanced RAG는 사슬을 유지한 채 앞뒤를 다듬고, Modular RAG는 단계 자체를 모듈로 갈아 끼운다. 그림은 세 방식을 같은 단계 축에 놓은 것이다.

표는 세 방식의 차이를 나타낸 것이다. (논문 2.1~2.3절)
기준Naive RAGAdvanced RAGModular RAG
검색 전없음indexing 최적화(슬라이딩 윈도, 메타데이터), query rewriting모듈로 더하거나 교체
검색 후없음reranking, context compression모듈로 더하거나 교체
흐름한 방향 사슬한 방향 사슬순서 변경, 반복, 분기

핵심 비교 Naive RAG는 검색 → 생성뿐, Advanced RAG는 앞뒤를 다듬고, Modular RAG는 단계와 순서를 바꾼다.

요약

Advanced RAG는 사슬을 지키며 검색 앞뒤를 다듬고, Modular RAG는 모듈의 종류와 순서까지 바꾼다.

핵심 질문
  • Modular RAG는 무엇을 바꿀 수 있게 하는가?
  • 새 패턴은 Naive RAG의 순서를 어떻게 바꾸는가?

Modular RAG의 패턴논문 2.3절

Modular RAG는 기능 모듈을 더하거나 갈아 끼울 수 있게 한다. 논문은 새 모듈로 Search, RAG-Fusion, Memory, Routing, Predict, Task Adapter의 6가지를 든다.

그림은 모듈의 순서를 바꾼 대표 패턴을 나타낸 것이다. 교과 색 칸이 Naive RAG에 새로 끼우거나 바꾼 모듈이다.

Naive RAG의 Retrieve-Read도 모듈 두 개를 고정 순서로 이은 경우이므로, 앞의 두 패러다임은 Modular RAG의 특수한 경우로 해석할 수 있다.

요약

Modular RAG는 모듈의 종류와 순서를 바꿔 Rewrite, Generate, 반복 Retrieve 같은 새 흐름을 만든다.

핵심 질문
  • Advanced RAG는 품질을 얻는 대신 무엇을 치르는가?
  • Modular RAG는 왜 운영하기 어려운가?
  • 응답 지연은 어느 단계에서 가장 크게 늘어나는가?

탐구 자료패러다임마다 치르는 대가

표는 세 패러다임의 장점과 대가를 논문 밖 후속 연구로 보충해 나타낸 것이다. Modular RAG의 흐름은 Gao et al. 2024를 따랐다.
패러다임장점단점·비용이럴 때 쓴다
Naive RAG단순하고 빠름검색 precision·recall이 낮아 잡음 문서가 그대로 들어감문서가 적고 질문이 단순할 때
Advanced RAG검색 전후 최적화로 품질이 오름query rewriting·reranking마다 모델 호출이 늘어 지연(Latency)과 비용이 커짐. rewriting이 틀리면 뒤 단계가 모두 틀림(오류 전파(Error Propagation)). 조정할 값이 많음(청크 크기, top-$k$, reranker 문턱값)품질이 중요하고 지연 여유가 있을 때
Modular RAG모듈 교체, routing, 반복으로 유연함linear·conditional·branching·loop 흐름이 늘어 디버깅과 관측이 어려움. 반복 검색은 지연이 들쭉날쭉하고 멈출 조건이 필요함. routing이 틀릴 수 있고, 단계마다 따로 평가해야 함질문 유형이 다양하고 운영 인력이 있을 때

한 서빙 실험(rewriter 8B, reranker 120M)에서는 rewriter를 넣으면 답을 한 토큰씩 이어 쓰는 자기회귀 생성(Autoregressive Generation) 때문에 TTFT(Time To First Token)가 2.4배로 늘었고, reranking은 영향이 작았다(RAGO, Jiang et al. 2025).

그림은 같은 질문 하나를 처리하는 시간을 단계별로 쌓은 것이다. 값은 예시이다. 교과 색 구간 = Naive RAG에 없던 단계(rewrite = query rewriting, rerank = reranking).

요약

Advanced RAG는 품질을, Modular RAG는 유연성을 얻는 대신 지연·비용·오류 전파·디버깅 부담을 치르므로 서비스 조건에 맞춰 고른다.

탐구 자료RAG, fine-tuning, 프롬프트 엔지니어링논문 2.4절

논문은 모델 최적화 방법을 외부 지식 필요도와 모델 적응 필요도의 두 축으로 비교한다. 그림은 그 비교를 나타낸 것이다.

1
프롬프트 엔지니어링(Prompt Engineering)

모델은 두고 지시와 예시만 다듬는다. 가장 싸다.

2
RAG

문서만 바꿔 실시간으로 갱신하고 근거를 보여 준다. 검색 때문에 응답이 늦고 데이터 검색의 윤리 문제가 따른다.

3
fine-tuning(미세 조정)

말투와 형식까지 깊게 맞추지만 갱신하려면 다시 학습해야 하고 계산 비용이 크다.

4
논문이 인용한 비교

기존·새 지식 모두에서 RAG가 비지도 fine-tuning보다 나았다는 연구를 든다.

논문은 두 방법이 서로 배타적이지 않으며 함께 쓰려면 여러 번 조정해야 할 수 있다고 본다.

요약

RAG는 외부 지식을, fine-tuning은 모델 적응을 맡으며 둘은 함께 쓸 수 있다.

핵심 질문
  • 규정이 바뀌면 세 방법은 각각 무엇을 바꾸는가?
  • 언제 RAG를 고르는가?

세 방법의 비교논문 2.4절

그림은 규정이 개정된 같은 상황에서 세 방법이 바꾸는 곳을 나타낸 것이다. 앞의 둘은 프롬프트를, fine-tuning은 모델 가중치를 바꾼다.

표는 세 방법의 쓰임을 나타낸 것이다. 비용 수준은 일반적인 경향이다.
방법언제 쓰나지식 갱신비용약점
프롬프트 엔지니어링지시·말투를 빠르게 바꿀 때프롬프트에 직접 써 넣음가장 낮음입력 길이 한도
RAG자주 바뀌는 지식에 근거가 필요할 때문서만 교체검색 구축·운영, 응답 지연검색이 틀리면 답도 틀림
fine-tuning말투·형식을 모델에 깊게 맞출 때다시 학습학습 계산 비용이 큼근거 제시가 어려움

핵심 비교 프롬프트 엔지니어링은 지시를 바꾸고, RAG는 모델 밖 지식을 바꾸며, fine-tuning은 모델 안 가중치를 바꾼다.

요약

지식이 자주 바뀌고 근거가 필요하면 RAG를, 모델의 말투와 형식을 깊게 맞추려면 fine-tuning을 쓴다.

핵심 정리
  • Naive RAG는 indexing, 검색, 생성을 한 번씩 거친다.
  • Advanced RAG는 검색 전·후를 최적화한다.
  • Modular RAG는 모듈의 종류와 순서를 바꾼다.
  • 패러다임마다 대가가 있다. 단계를 더하면 지연·비용·오류 전파·디버깅 부담이 커진다.
  • 패러다임 문항은 사슬 구조를 지키는지, 순서를 바꾸는지부터 가려라.
